# qh

qh is a small coding agent for Qwen models on an OpenAI-compatible server. I wrote it for Qwen3.8-27B and Qwen3.6-35B-A3B on `mlx_lm.server`, on a MacBook. It is one Go binary and uses only the standard library.

The daemon listens on a Unix socket (`~/.qh/qh.sock`). It keeps the sessions and runs the agent loop. `qh run` and the chat client connect to it, and the first call starts it. It builds on Linux and macOS.

The socket takes one JSON line per connection. `run` streams the events of a run back; `attach` streams every event of a session (first its history) until the client leaves; `cancel` stops the active run. Runs on one session go one at a time, in order.

## Differences from pi

I used pi with these models first. Some things cost time:

- The Qwen chat template reads earlier thinking from `reasoning_content`. pi sends it back as `reasoning`, so the template drops it. In a tool loop the model loses its plan after each call and works it out again.
- Thinking sometimes loops ("wait, let me check the parser again...") until it reaches `max_tokens`.
- The system prompt and the edit tool are written for many models. The edit tool takes an array of objects, and Qwen gets the JSON wrong more often than with flat arguments.

What qh does:

- It sends the thinking back as `reasoning_content` and sets `preserve_thinking`. Each request is then the previous prompt plus new messages, which is what the server's prompt cache can reuse. (The Qwen 3.5+ models have linear-attention layers; their cache can't be trimmed, so a prompt that differs in the middle is processed again from that point.)
- Without `preserve_thinking` the Qwen3.6 template drops the thinking of every assistant turn before the last user message, so qh's own messages in a run (the self-check, the fix turn) would change the prompt and lose the cache. qh keeps it on and instead clears the thinking of earlier runs itself, once, at the start of a new run, when it holds at least 8000 tokens and 15% of the context. That costs one cache miss and keeps the rest of the session smaller. Measured on the 37 Mac sessions (2026-11-08, one pass): dropping old-run thinking cuts the prompt tokens summed over all requests by 6%, all of it in the 19 sessions with more than one run, and the biggest of those lose 15 to 27% of their final context.
- When the thinking repeats itself or passes `think_budget` characters, qh stops the step and asks again with thinking off.
- A normal run has ten tools: read, write, edit, bash, bg, grep, glob, todo, lookup and explore (explore can be turned off). grep searches file contents with a Go regular expression, or plain text with `literal: true`, and takes a `glob` filter such as `src/**/*Test.kt`. It returns at most 100 `file:line:text` lines, then `[N more]`. glob lists files by path pattern (`**` matches any number of directories), at most 200. Both skip hidden folders (`.git`, `.gradle`, `.cargo`, `.venv`) unless the search starts inside one, and `build`, `target`, `vendor`, `node_modules` and `__pycache__`, and work the same on Linux and macOS since they do not call the system grep. The system prompt sends searches to them and keeps bash for git, builds and tests. edit takes one `old`/`new` pair. It still matches when the model copies the line numbers from read or drops trailing spaces. When `old` is not in the file, the error shows the closest lines with their numbers, so the model can copy them without reading the file again. When the model leaves out `path` and only one file holds `old`, qh edits that file and says so. When nothing matches exactly, lines that look nearly the same are used to find the place. write says how many lines it added and removed compared with the old file. When `old` appears more than once, the error shows each match with the lines around it, and `line=N` (or `offset=N`) picks the match nearest to line N. Two repairs are made only when exactly one place fits, and the result says what qh did: when `old` matches with every line shifted by the same indentation, qh shifts `new` the same way; when `old` is in several places but only one of them is whole lines (`import a.User` next to `import a.UserRepository`), qh changes that one. A read of a folder lists it. A read of a missing file returns the right file when there is exactly one with that name (or one that declares a type of that name), with a note; with several, it lists them. A grep or rg that finds nothing is not counted as a failed call. When grep or rg in bash rejects a pattern (an unescaped `(` and the like), the result says to use `-F` for a literal search; the grep tool says to set `literal`. A read-only run (`-ro`) gets read, grep and ls, and no shell.
- `bash` with `background: true` starts a server or watcher in its own process group and returns after 3 s (or when it exits) with an id such as `bg1` and what it printed so far. qh keeps the last 2000 lines of its output. `bg {"id": "bg1", "action": "read"}` returns the lines printed since the last read, at most 100, then `[N more, read again]`; `"action": "stop"` sends SIGTERM to the group and SIGKILL 2 s later. At most 3 run at once; a 4th is refused with the list of running ones. When one exits on its own, the next tool result says `bg1 exited with code N`, once. At the end of a run (report, step limit or cancel) qh stops every background command the run started and the report says which; the Done-when checks run before that, so they can test against a server. A daemon stop or SIGTERM kills them too. A daemon killed with SIGKILL leaves them running.
- explore hands a question about the code ("where is the security filter chain configured, and which beans does it use?") to a read-only helper run. The helper has read, grep, glob and ls, a fresh context, a short fixed system prompt (so its prefix stays in the server's cache across calls) and 15 steps (`explore_steps`). At the limit it is told to answer from what it found. The run gets back only the answer, at most 60 lines, with `file:line` references; the search output stays out of its context. The helper's requests wait at the same gate as every other request. Its tool calls show indented under the explore line in `qh run` and the chat, and the stats line ends with `explore: N runs, N steps, N tokens out` (these are not in the main step and token counts). The system prompt says to use explore for a question that needs more than 3 searches and to read a known file directly. After 5 search calls in a row (grep, glob, read, ls, or a bash `grep`, `rg` or `find`) with no other call between them, once the context is past 30k tokens, the 5th result ends with a note that explore keeps such results out of the context; this happens once per run. `"explore": false` in the config removes the tool and that line.
- todo is a checklist: one `items` argument, a list of `{text, status}` with status pending, doing or done, and each call replaces the list. The system prompt asks for one on tasks with 3 or more steps. The list is saved with the session, so it survives a resume; `-new` and reset clear it. The TUI and `qh run` show one line per change (`todo done: fix parse`). Every 15 steps, and after the first tool call that follows a compaction, the tool result ends with the open items. The self-check names the open items as not done, and the report ends with `qh: todo items not done:` when some are left.
- lookup answers "does this library have X, and what is its import?" from the project's own jars, since qh blocks digging in jars. It takes one `name` (`routes`, `RedisRateLimiter`, or a dotted name) and returns at most 10 lines like `import org.springframework.cloud.gateway.route.builder.routes  (fun, spring-cloud-gateway-server-4.3.5.jar)`, or "not found in the project's libraries". It lists classes (nested ones as `Outer.Inner`) and the top-level Kotlin functions and properties of `*Kt` facade classes, read from the class files' constant pools. For `Receiver.fun` with no match it answers for `fun` and says so. The jars are the project's resolved compile and test classpath: Gradle runs a small init script (`--offline` first), Maven runs `dependency:build-classpath`. When that fails, qh takes the newest cached version of each artifact of the groups named in the build files, and the answer says so. The index lives in `~/.qh/lookup/` and is built again when a build file changes. On realupscaler (201 jars, 60k names) the first lookup takes 1.2 s on this PC with a running Gradle daemon (about 12 s with a cold one) and 3.5 s on the Mac; later ones take 0.02 s. On gr-printing (Maven, 212 jars) the first takes 1.6 s. JDK classes are not indexed (`lib/modules` is a jimage file). The library-digging notes point the model to lookup. `qh lookup [-C dir] NAME` runs it from the shell.
- After a write or edit that succeeds, qh runs a checker on that file and appends its errors in that file (at most 10 lines, `file:line:col message`) to the result. Nothing is added when the file is clean. The model then fixes a typo at once, not after a 60 s build. See `diagnostics` below.
- qh keeps what it last showed the model of each file (by read, or its own write or edit). An edit or write on a file that changed since then (another process, a formatter, the user) is refused once with the changed lines, at most 20; the next call goes through. A write on an existing file the model never read is refused once ("read it first, write replaces the whole file"); an edit on one is allowed, since `old` must match anyway. Files changed by the model's own bash command, and qh's own formatting and import fixes, update the record and never trip this.
- If the server leaves a `<tool_call>` block in the text, qh parses it.
- The third identical tool call gets a note that the result will not change.
- When the task has a "Done when" line, qh asks the model once, before the final report, to check each requirement and fix what is missing. For each test assertion it must name the smallest wrong implementation and say whether the assertion fails on it, which catches tests that cannot fail. Assertions in changed test files that check for absence (`doesNotContain`, `assertFalse`, `wasNot Called`) are quoted back too, with the question of what the value holds when the code is right, since they pass on an empty or encoded value. Assertions that expect null for a field the task gives a value to ("score 0.01" in the task, `assertThat(log.moderationScore).isNull()` in the test) are quoted with that part of the task, and so are test lines that empty a whole table or store (`DELETE FROM` without `WHERE`, `TRUNCATE`, `flushAll`), which break other test classes sharing the database. It also lists, for each try/catch it wrote, the calls in the try that can throw the caught type, so a catch meant for one call does not swallow errors from the next. The lines of the task that say what not to do ("do not", "never", "not any()") or give an exact rule ("or blank", "at least", "only if") are quoted back one by one, since the model slips on those most. In a normal (not read-only) run it then runs the commands in backticks on that line, such as `./mvnw -q test` or `grep -n TODO src/A.kt` (build and test tools, plus read-only ones like grep, rg, test, diff and git diff). "`./gradlew test` x4" (or "4 times") runs the check that many times, and each run must pass (`qh check passed 4 of 4 runs`). When the run wrote or edited a test file, a test check that passed runs a second time (Gradle with `--rerun-tasks`); if it fails then, it is reported as `qh check FAILED (flaky: passed 1 of 2 runs)` and the model gets a turn to fix the flaky test. When the task has a "Change only:" line (with the files on it or in a list under it), the self-check names the files the run changed outside that list and asks the model to undo them or give the reason under "Changed outside the brief:", and the facts block lists them. A backticked command it does not run is listed as `qh check skipped`, and the verdict line counts it. Commands that exit 0 whatever they print (`git status`, `git diff` without `--exit-code`, `ls`, `cat`, `find`) are listed as `qh check info` with the first lines of their output, not as passed. Words after a command can say what it must print: "`git diff --name-only` prints nothing" (or "is empty") fails on any output, and "`git status --short` shows no `.bak` file" fails on a line that contains `.bak`. If one fails, the model gets the output and one more turn, and the commands run again after it; the report starts with a one-line verdict (`qh: all 2 Done-when checks passed after the run`) and ends with one `qh check passed:` or `qh check FAILED:` line per command. When the task asks for no warnings or no unused code, compiler warnings in the check output count as a failure for that turn (see `warn_ignore` below). qh also reads the Kotlin and Java files that the run wrote or edited, and lists each import whose name is not used again in the file (kotlinc does not warn about these); the model gets one turn to remove them. The same turn covers annotations: when a code block in the task puts `@Component` on `class MailRenderer` and the file that declares `MailRenderer` lacks it, qh says so (tests that build the class by hand pass without it). Lines in changed test files that open private members by reflection (`getDeclaredField`, `isAccessible = true`, `ReflectionTestUtils`) are flagged in that turn too, and so are Spring Cloud Gateway Kotlin routes with two predicate calls on separate lines (`path(...)` then `method(...)`: the second replaces the first). When checks failed and the report blames the environment ("test environment issue", "the code is correct", "flaky"), the verdict line says that claim is not checked. When it has no turn left (after the fix turn, or at the step limit), qh deletes those import lines itself before the checks, so a wrong removal shows as a failed build.
- The model server answers one request at a time, so the daemon sends one at a time. A run on another session waits and shows "waiting for the model".
- Tool output longer than 12000 characters is cut in the middle. The end is kept, since errors are usually there.
- A read with no offset or limit of a file over 400 lines returns lines 1 to 200 and an outline of the rest: the line numbers of the func, fun, def, class and method declarations (at most 80), so the model reads the part it needs with offset.
- A read of a file the model already read in this session, in the same range or as a whole, gets "unchanged since your read at step N (L lines)" when the file is the same (size and hash) and that earlier result is still in the context. After a compaction, or when the model asks the same read again right after the note, it gets the content.
- When a Gradle or Maven command passes, its `> Task :...` lines, progress bars and download lines are left out, with one line that says how many. A failed build keeps every line.
- The stats JSON has `ctx_by_tool`, the tokens (characters / 4) that each tool's results hold in the context at the end. Past 40k tokens the `qh run` stats line adds the top three, for example `(ctx: read 41%, bash 33%, grep 9%)`. In the 37 sessions on the Mac (about 1.6M tokens, 2026-11-08), read results were 38%, thinking 26% and bash 22%.

## Install

```sh
go install github.com/ozzenerol/qh@latest
```

or clone the repo and run `go build`.

## Use

```sh
qh run "the parser tests fail since the last commit; find out why and fix it"
qh run -s lexer -C ~/src/iris -new "add a test for the new duration literals"
echo "long task text" | qh run -
qh run -ro -timeout 10m "where is the config file parsed?"
qh                # chat in this directory, in a new session
qh -c             # continue the newest session of this directory
qh -r             # pick a session to resume
qh compact -s lexer "keep the test names"
qh wait -s lexer  # block until the run on lexer ends, then print its report
qh sessions
qh top            # live view of every daemon (~/.qh, ~/.qh-*) and its runs
qh reset -s lexer
qh undo -s lexer  # put back the files the last run on lexer changed
qh diff -s lexer  # what the last run on lexer changed, as a unified diff
qh stop
```

`qh wait -s NAME` waits for the run that is going on a session (started from anywhere) and prints its report and stats line the same way, with exit code 4 at the step limit. `qh run` prints the final report on stdout. The first line on stderr names the session, each tool call is one line, and the last line has the steps, tool errors (calls that were wrong: bad arguments, an edit that does not match, a missing file, a shell or flag mistake, a timeout), failed commands (commands that ran and exited non-zero, such as a failing build or test, which are answers, not errors), tokens, time and context size (with a hint to start a new session or compact past 80k tokens or 60% of the window). After a `|` it says where the time went: how fast the model writes (tokens per second while writing), how long it spent reading the prompt before its answers, the time in tools (builds, tests, searches), and any wait for another session. Ctrl+C cancels the run and the daemon kills the running command. At `-timeout` the daemon stops the model, still runs the Done-when checks and the final checks on the files as the run left them (up to 10 more minutes), prints the report with the facts, and `qh run` exits with 124. The model sees `[qh: step N of M]` every 10 steps. The passes that qh asks for after the model's answer (the self-check and the fix turn after the checks) each add 15 steps to the limit, so a finished task does not run out of steps in the clean-up. A run that reaches the limit gets a warning 5 steps before, then a request for the report (a tool call there gets "tools are off" and up to two more tries), and `qh run` exits with 4. When a command fails and left JUnit XML reports (Gradle `test-results`, Maven `surefire-reports`), the tool result ends with the failing tests, their messages and the top of each stack. For a status mismatch (`Status expected:<401> but was:<200>`) it adds the response body from the report; when the body holds the expected status, it says the status was never set. Test commands (gradle, mvn, `test`, `check`) get this even with exit 0, since `./gradlew test | tail` exits 0. They also end with a count from those reports, such as `[qh: tests: 34 passed, 1 failed, 0 skipped (MailProcessorTest 12, RetryQueueIT 23)]`, and a passing Done-when check carries that count in its `qh check passed:` line. A failed build also gets every compiler error as one `file:line:col message` line (Kotlin `e:`, javac and gcc `error:`, Maven `[ERROR]`), so they are not lost in a cut tail. For an unresolved name from MockK, AssertJ, JUnit or the MockMvc matchers (`just`, `Runs`, `every`, `assertThat`), the import line follows. After three commands in a row that dig in library jars or caches (`unzip`, `javap`, `~/.gradle/caches`, `~/.m2`) with no passing build or test run between them, the model is told to stop and gets the last compiler errors again (or, before any build failed, to write the code and compile it). After the second time, such commands are blocked for the rest of the run, and from the second blocked command on the reply repeats the last compiler errors. When tests fail and the run changed main code that uses Reactor (`Mono`, `Flux`), the first failing result also gets a short hint about empty Monos, which fail with no exception. After 8 (and again 16) writes or edits to test files with no change to the main code between them, the model is told the tests may be right and to check the main code against the failure. A bash command that deletes a folder with `rm -r` is counted in the stats line (`3 rm -r`), and the third deletion of the same path in a run gets a note that deleting caches rarely fixes a build. When `sed -i` fails with a BSD sed error (macOS), the reply says to use `sed -i ''` or the edit tool. At the end of a normal run, the report lists new untracked backup files (`.bak`, `.orig`, `.rej`, `.tmp`, `~`) that the run left behind. A call to `find`, which is not in the tool list, runs glob.

The chat shows every run on its session, from any client. The session name `@chat` means the chat that is open in a terminal (the newest one, if there are several). When Claude runs `qh run -s @chat -from opus "..."`, the open chat prints the message with an `opus` label and streams the answer. Messages that arrive during a run wait in a queue, and the chat shows them as queued. Esc or Ctrl+C stops the run that is active, whoever started it.

Each turn in the chat starts with who wrote it (`you`, `qwen`, or a label such as `opus`). Each tool call is one line with the tool, its target, a short result (`49 lines`, `3 hits`, `+2 −1`, `exit 1`) and the time it took; a failed call is red and has its first error line under it. Thinking folds into one line (`∴ thought for 6s · 3.1k chars`) unless Ctrl+T shows it. While the model thinks, the line above the input shows how much of `think_budget` the step has used. When someone else's run is going on the session, the input says so, and what you type waits in the queue. The line under the input has the session, the model, and the context with a meter.

In the chat, Enter sends and Ctrl+J starts a new line (pasted text keeps its lines). Up and Down walk the history, Ctrl+T shows the thinking, Ctrl+R opens the session list, and Ctrl+C twice quits. Editing keys work as in a shell: Ctrl+W, Alt+Backspace or Ctrl+Backspace delete the word before the cursor, Alt+D or Ctrl+Delete the word after it, Ctrl+U and Ctrl+K delete to the start or end of the line, Ctrl+Y puts back what the last delete removed, Alt+Left/Right, Ctrl+Left/Right or Alt+B/F move by word, and Ctrl+A/E go to the start or end of the line. `/help` lists all keys. Type `/` for the command menu (`/new`, `/resume`, `/think on|off`, `/sessions`, `/clear`, `/exit`); ↑↓ picks one, Tab completes, Enter runs it. Without a terminal (a pipe, or `TERM=dumb`) qh uses a plain line chat.

Sessions are saved in `~/.qh/sessions/NAME.json` after each step, so they survive a daemon restart. `qh sessions` lists them with the number of turns, the context size, and `RUNNING step N` for a run in progress (`WAITING for the model` while another session's run has the model), and who started it (`from opus`, `from qh run`, `from a terminal chat`). The session list in the chat (Ctrl+R or `/resume`) shows who started each session, its turns, context and age, and marks the ones near the compaction point. `d` deletes the selected session and `x` deletes every finished session that a `qh run` or another program started; sessions with a run going or open in a chat stay. `qh top` polls every daemon folder (`~/.qh` and `~/.qh-*`) once a second and shows its model server, the runs going on it, and the sessions of the last hour; with two daemons and 80 columns they sit side by side. A chat started with plain `qh` gets a new session named after the time (`1108-013105`); `qh run` uses `main` unless you give `-s`.

## Report facts

A normal run's report ends with lines that qh writes itself, from what it saw (at most 10 files are listed):

```
qh facts: the run changed 3 files:
  modified src/A.kt (+1 -1)
  created src/B.kt (+40 -0)
  modified src/F.kt (+4 -4) whitespace only
qh facts: last test run qh saw: 34 passed, 1 failed, 0 skipped
qh facts: stopped the background commands still running at the end: bg1 (./gradlew bootRun)
qh note: the report lists Other.kt as changed, but this run did not change it
qh note: the run created src/B.kt, and the report does not mention it
qh note: the report says "35 tests passed", but no test run qh saw had 35 tests
qh note: the report says "all tests pass", but the last test run qh saw had 1 failed
```

The files come from the undo checkpoint, so they include changes made by bash in a git repo. The test counts are the `[qh: tests: ...]` lines from JUnit XML reports (Gradle, Maven); runs with no such reports get no test facts and no test notes. The claim check is literal: file names are the base names on the report's "files changed" (or created, modified) lines and the list items under them; a changed file counts as mentioned when its base name is anywhere in the report, and test files and whitespace-only changes are not asked for. A test number in the report ("35 tests passed", "12 passed") is fine when it matches the passed count, the total or a per-class count of any test run in the run. On the final reports of 34 stored Mac sessions it gave 3 test-number notes, two of them for numbers qh has no facts for (one class's passes inside a failing class, "the 3 passing tests") and one for a sentence about what 44 would mean.

`qh diff -s NAME` prints the unified diff of the newest run's files against how they are now, read from the checkpoint, so it works in a repo with other uncommitted work. When the last run changed nothing it says so.

## Undo

Before a run first changes a file with write or edit, qh copies the file (or notes that it did not exist) to `~/.qh/sessions/NAME.undo/RUN/`. Only touched files are kept, files over 2 MB are listed but not copied, and each session keeps its last 5 runs that changed something. In a git repo, bash commands are covered too: qh runs `git status` before and after each call (2 to 17 ms in repos of 20 to 546 files) and keeps the files the call changed, from `git show HEAD:path` when the file was clean before, from a copy taken before the call when it was already dirty, and as "did not exist" when it is new and untracked. A background command is covered the same way, from its start to the end of the run. Outside a git repo only write and edit are covered. Read-only runs keep nothing.

`qh undo -s NAME` restores every file of the newest run on that session, deletes the files it created, prints the list, and drops that checkpoint, so the next `qh undo` goes one run further back. It refuses, and names the files, when one changed after the run ended, or when the run has not finished; `-force` restores anyway. `qh undo -s NAME -list` shows the runs it can undo, newest first. The session's messages stay as they are. A reset or a compaction makes qh forget which files the model has read, so a write needs a new read after them.

## Compaction

When a request passes 80% of `context` (262144 tokens by default), qh asks the model for a summary of the conversation and replaces the messages with it. This happens before a new prompt, or between two steps of a run; in the second case the model gets "continue the task from the summary". `/compact [focus]` in the chat, or `qh compact -s NAME [focus]`, does it by hand. The summary request is the normal prompt plus one question, so the server reads the whole conversation from its cache and only writes the summary. The old messages go to `~/.qh/sessions/archive/`. In the chat, Ctrl+O shows or hides the last summary above the input box.

I use it with Claude Code as the coordinator. Claude writes the task, runs `qh run -s NAME "..."` and reads the report, then checks the diff itself. A second `qh run -s NAME` continues the same session, so a correction does not need the whole brief again.

On a small test (one failing Python test, Qwen3.6-35B-A3B on an M3 Max), qh fixed it in 9.6 s and pi in 11.7 s. That is one run each, not a benchmark.

## Eval

`qh eval` runs a fixed set of tasks through the agent of the binary that runs it (not the daemon), so two builds can be compared on the same work. Each task is one file in `eval/` and is built into the binary: the prompt, a `check.sh`, and the files of a small repo, each after a `-- path --` line. qh writes the files to a temp git repo, runs the prompt there, then runs `check.sh` in the repo; exit code 0 is a pass. `check.sh` lives outside the repo, so the model cannot read it, and it brings its own hidden tests.

Eight tasks come from mistakes seen in real runs: a 401 whose status is never set (`status-401`), tests that pass on wrong code (`weak-test`, checked against five mutants of the function), a JSON struct tag (`json-tag`), an import left unused after a rewrite (`unused-import`), a "do not modify the caller's slice" rule (`do-not-rule`), a range checked at and past its ends (`page-limit`), an error check that swallows more than the missing-file case (`swallowed-error`), and backup files left by `sed -i.bak` (`backup-file`). Seven are Go, one is Python; none needs the network. Two more test explore on a 20-package repo built by the task's `setup.sh`: `needle-timeout` (the /export timeout is shared with /reports through a helper in another file, so the obvious change breaks /reports) and `needle-question` (name the one function that sets `X-Request-Id`, among 40 lines that mention it).

```sh
qh eval                          # every task once
qh eval -only status-401,page-limit -n 3
qh eval -list
qh eval -compare ~/.qh/eval/A.json ~/.qh/eval/B.json
```

Each run prints one line: pass or fail, steps, failed tool calls (tool errors plus failed commands, as before they were split; the JSON has both), the size of the last request, fresh tokens (prompt tokens that the server did not have in its cache, summed over the requests), output tokens and seconds. The results go to `~/.qh/eval/DATE.json` with the version, the git commit of the build and the model. `-compare` prints the pass count and the means per task for both files. `-dir DIR` reads `.task` files from a folder, `-timeout` limits each task (20m by default), `-v` prints the tool calls, and `-noexplore` turns explore off for the run (the JSON file records which). The eval sends its requests straight to the model server, not through the daemon, so it should run when no other run uses the model.

## Prompt cache

The server reuses its cache for the part of a request that matches an earlier one from the start, so qh never changes a message once it was sent. Notes such as `[qh: step N of M]` go into the newest tool result before it is sent, and later hints come as new messages. The system prompt is built once per session and kept in the session file, so a run that edits `AGENTS.md` or adds a source folder does not change it; it is built again for a new or reset session, after compaction, when the folder or the read-only mode changes, and when a new qh build has other prompt templates or tools (so an older session gets the prompt that names its tools). When a run is stopped between tool calls, the next run first answers the open calls with "interrupted". A test (`TestPromptOnlyGrows`) runs two turns, a compaction and a third turn through a fake model and checks that each request starts with the exact messages of the one before; `TestMixedToolsPromptOnlyGrows` does the same for a run that uses todo, a background command, write, edit with diagnostics, explore and a repeated read.

## Config

`~/.qh/config.json` (every field is optional):

```json
{
  "url": "http://127.0.0.1:8080/v1",
  "model": "",
  "max_steps": 120,
  "max_tokens": 16384,
  "think_budget": 30000,
  "context": 262144,
  "compact_at": 0,
  "warn_ignore": [],
  "explore": true,
  "explore_steps": 15,
  "confine": true,
  "read_roots": ["~/.m2/repository", "~/.gradle/caches", "~/go/pkg/mod", "/usr/local/go/src"],
  "web": false,
  "search_url": "",
  "sort_imports": false,
  "format": {".go": "gofmt -w"},
  "diagnostics": {".py": ""},
  "diagnostics_timeout": 20,
  "repos": {"myrepo": {"sort_imports": true, "format": {".kt": "ktlint -F"}}}
}
```

An empty `model` means the first model the server lists. `compact_at` 0 means 80% of `context`. `warn_ignore` holds regular expressions for compiler warning lines that the "Done when" checks should not count. Only compiler warnings count (Kotlin `w:`, `file:line: warning:`, Maven compiler `[WARNING] File.java:[l,c]`); JVM notices such as `WARNING: sun.misc.Unsafe` do not.

The file tools (read, grep, ls, glob, write, edit) stay inside the project: the git root of the working directory, or the working directory when it is in no repo. read, grep, ls and glob may also use the `read_roots` folders, by default the Maven, Gradle and Go module caches and the Go sources, so a run can read library code. A path outside gets an error, and symlinks count by where they point. bash is not limited. `"confine": false` turns this off.

Web tools are off by default. `qh run -web`, `qh -web` or `/web on` in the chat turn on `web_search` and `fetch_url` for the session (`/web off` turns them off again), and `"web": true` gives them to every new session. `web_search` asks a SearXNG instance at `search_url` through its JSON API (`json` has to be in `search.formats` in SearXNG's settings.yml) and returns 8 results with title, URL and snippet. `fetch_url` returns a page as plain text, 10000 characters per call, with headings, list items and `pre` blocks kept; `offset` reads further. qh has no built-in search engine: DuckDuckGo's HTML page answered HTTP 202 (a bot check) from the second request on in a test, so it uses SearXNG. Turning web on or off changes the tool list, so the next request misses the prompt cache once.

After the model's final answer, qh can tidy the files the run wrote or edited, before the checks run. `sort_imports` sorts the imports of Kotlin files (IntelliJ layout: other packages, then `java`, `javax`, `kotlin`, then aliases) and Java files (static imports last). `format` maps a file extension to a command, and qh appends the changed files of that type. `repos` sets both for one repo, by the folder name of its git root. In Kotlin and Java files it always indents a declaration that sits at column 0 inside a class body, with the block that follows it (that compiles, so nothing else catches it). The report lists what qh changed. `QH_URL`, `QH_MODEL`, `QH_HOME` and `QH_SOCK` override the file.

`diagnostics` maps a file extension to the checker that runs after each write or edit. `{file}` and `{dir}` in the command become the file and its folder; with neither, the file goes at the end. qh keeps the output lines of the form `path:line:col: message` that point into that file. The defaults use only tools it finds on PATH (or in `~/go/bin`, `/usr/local/go/bin`, `~/.local/bin`): `.go` runs `go vet` on the package (`gopls check -severity=error` when there is no `go`), `.py` compiles the file with `python3` without writing a `.pyc`, and `.kt` runs `ktlint` for syntax errors only (it has no classpath, so type errors still need the build). An empty command turns a default off. `diagnostics_timeout` is in seconds (default 20); a check that takes longer adds nothing. `repos` can set both per repo. On qh itself (7k lines) an edit with the `go vet` check takes 77 to 92 ms, 10 runs each; `gopls check` takes 1.1 s on a clean file.

The system prompt is about 150 words. qh adds `~/.qh/AGENTS.md`, then `~/.qh/notes/REPO.md` (REPO is the folder name of the git repo that holds the working directory; a good place for API facts and repo notes that should not be committed), then `AGENTS.md` (or `CLAUDE.md` when a directory has no `AGENTS.md`) from `/` down to the working directory. In a git repo it also lists where the code lives: the module roots (folders with `go.mod`, `package.json`, `build.gradle.kts`, `pom.xml` and the like) and the `src/main|test/kotlin|java|...` folders, at most 40 lines, so the model does not guess which module holds a class.
